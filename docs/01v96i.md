# Yamaha 01V96i — SysEx reference (reverse-engineered)

Everything this project knows about the mixer's MIDI output, in one place. This is the
authoritative reference for the 01v-specific data; the code should never be the only place
a byte layout or scaling formula lives.

> **Provenance.** All byte layouts and value encodings below were reverse-engineered by
> observing the MIDI stream of a Yamaha 01V96i while building this bridge. They are
> behavioural facts about what this particular console sends — not a transcript of official
> documentation. Each item is tagged:
>
> - **[obs]** — directly observed; the running code relies on it.
> - **[fit]** — formula fitted empirically to observed data; it works, but the exact raw
>   byte ranges have not been systematically verified.
> - **[hyp]** — hypothesis; needs a capture session to confirm.
>
> When the mixer is next connected, work through the

## 0. Sources

Two authoritative sources now back this document, alongside the captures:

- **Yamaha, *01V96i Reference Manual*** (`docs/manuals/01v96i_reference_manual.pdf`,
  186 pp), §2.8.3 "Parameter change".
  Defines the framing, the address space and the shape of the data field. Facts taken from
  it are tagged **[doc]** and outrank any earlier curve fit.
- **On-device captures**, August 2026, logged with `tools/monitor.py` into `captures/`.
  Tagged **[obs]**.

The *01V96i Owner's Manual* is alongside it. Yamaha's separate *MIDI Protocol for 01V96i*
document — which carries the element and parameter number tables, and the fader raw↔dB
table — is no longer distributed by Yamaha
and could not be found anywhere, including the Wayback Machine. Element numbers below were
therefore recovered from captures and cross-checked against the independent
[kryops/01v96-remote](https://github.com/kryops/01v96-remote) project.

### Console configuration

Two console pages matter. Reference Manual pp. 101–102.

#### `DIO/SETUP` → `DIO/Setup | MIDI/Host`

The port assignments on this page are what decide which of the eight USB ports does what.
The configuration this was all developed against:

| Setting | Value on this console | Role |
| --- | --- | --- |
| **Studio Manager** | **USB 1**, ID 1 | **The port the bridge uses.** Full bidirectional parameter-change channel. |
| Rx PORT | USB 4 | General MIDI *reception* (program/control changes). Not used by the bridge. |
| Tx PORT | USB 5 | General MIDI *transmission*. Mirrors a subset of parameter changes. |
| DAW | USB 2–3 | Reserved for a DAW control-surface protocol. |
| MMC | Device ID 1 | Machine control; unrelated. |

What each port does, measured on device: **[obs]**

| Direction | Studio Manager (USB 1) | Rx PORT (USB 4) | Tx PORT (USB 5) |
| --- | --- | --- | --- |
| Console → bridge | Everything: keepalive, all parameter changes, both mute forms | — | Form A parameter changes only |
| Bridge → console | Accepted | Accepted | — |

**Either configuration works.** Measured on device:

- **Sending** succeeds on the Studio Manager port *and* on the Rx PORT — a fader moved from
  the bridge in both cases.
- **Receiving** on the Tx PORT delivers everything the bridge uses, including solo in the
  Setup address space. It omits only the keepalive and the Form B mirrors, and neither
  matters: Form B duplicates Form A exactly, and the keepalive exists only to auto-detect a
  port you are naming explicitly anyway.
- The Studio Manager port additionally carries those two, which makes it the better choice
  when probing for the console rather than configuring it by name.

So the natural configuration is **listen on the Tx PORT, send on the Rx PORT** — the roles
the console's own settings name — with the Studio Manager port as the alternative when a
single port for both directions is wanted:

```bash
python3 main.py --midi-in "MIDI 5" --midi-out "MIDI 4"
```

Consequences:

- Nothing the bridge acts on is lost by using Tx/Rx.
- Auto-detection by keepalive only works on the Studio Manager port, so a bridge configured
  for Tx/Rx must be given its ports by name.
- The **DAW** port pair (USB 2–3 here) is where a Mackie Control / HUI surface protocol
  would live — relevant to the planned REAPER backend, which may be better served by that
  than by SysEx.

#### `MIDI` → `[F1]` → `MIDI | Setup`

| Row | Setting | Needs to be | Why |
| --- | --- | --- | --- |
| CHANNEL | Tx / Rx | **1** | The device number is the MIDI channel. The bridge hardcodes `0x10`, i.e. n = 0 (device 1); any other value and every mask misses. |
| PARAMETER CHANGE | **Tx** | **ON** | Without it the console sends nothing when a control moves. |
| PARAMETER CHANGE | **Rx** | **ON** | Without it the console ignores everything the bridge sends. |
| PARAMETER CHANGE | ECHO | off | Echoes received messages back out; would loop with the bridge. |
| — | **Fader Resolution** | **HIGH** | HIGH gives the full 1024-step range this document assumes. **LOW switches faders to 256 steps**, which would silently break `FADER_LAW` and every dB reading. The observed maximum of 1023 confirms HIGH. **[obs]** |

BULK Rx and the OTHER COMMANDS echo are irrelevant to the bridge.

### MIDI port

Of the eight USB-MIDI ports, only two carried traffic in the configuration above:

| Port | Assigned as | Carries |
| --- | --- | --- |
| `01V96i MIDI 1` | Studio Manager | Everything: keepalive, all Form A parameter changes, Form B mutes. Accepts parameter changes *in*. |
| `01V96i MIDI 5` | Tx PORT | Form A parameter changes only — a subset, outbound only |

Use the **Studio Manager port**. Probing for the keepalive finds it, since that is the only
port it appears on. **[obs]**

## 1. Transport and framing

- Input is a standard MIDI DIN/USB connection from the mixer, read with `mido`.
- The console emits MIDI **System Exclusive** messages for control movements.
- `mido` delivers them as `msg.type == "sysex"` with `msg.data` = the bytes **between**
  `F0` and `F7` (the framing bytes are stripped). Below, data bytes are numbered
  **B0…B11** (B0 is the first byte after `F0`).
- All known control messages are **12 data bytes** long, except one 5-byte message that is
  ignored (see catalogue). **[obs]**

## 2. Common header

The Reference Manual §2.8.3 defines the layout; the bridge's byte numbering maps onto it
directly. **[doc]**

| Byte | Value | Manual field | Meaning |
| --- | --- | --- | --- |
| B0 | `0x43` | ID No. | Yamaha manufacturer ID |
| B1 | `0x10` | SUB STATUS `1n` | n = device number = MIDI channel; `0x10` → n = 0 |
| B2 | `0x3E` | GROUP ID | Digital mixer |
| B3 | `0x7F` / `0x1A` | MODEL ID | `7F` = Universal, `1A` = 01V96i-specific |
| B4 | `0x01` / `0x04` | ADDRESS | `01` = Edit Buffer, `04` = Backup data |
| B5 | varies | **Element no.** | Which control family (fader, mute, EQ, …) |
| B6 | varies | **Parameter no.** | Which parameter within that element |
| B7 | varies | **Channel no.** | 0-based channel, or a slot selector for masters |
| B8–B11 | varies | **data** | One value in four 7-bit bytes — see [§4](#4-value-encodings) |

The bridge's older names map as: "selector" = Element no., "param" = Parameter no.,
and `u`/`v` are simply the last two of the four data bytes.

### Two message forms

Both forms are the same structure at different addresses:

- **Form A** — `43 10 3E 7F 01 …` — MODEL ID Universal, ADDRESS Edit Buffer.
  Carries faders, mutes, pan, surround X/Y and EQ.
- **Form B** — `43 10 3E 1A 04 …` — MODEL ID 01V96i, ADDRESS Backup data.
  Mirrors the ON/mute family, and carries a global solo status (`0x30`).
- **Form C** — `43 10 3E 1A 03 …` — MODEL ID 01V96i, ADDRESS **Setup data**.
  Carries **solo** (element `0x2E`). Solo does not appear in the edit buffer at all.
  **[obs]**
- **Form D** — `43 10 3E 1A 02 …` — MODEL ID 01V96i, ADDRESS **Patch data**.
  Carries **channel names** (element `0x04`) — see [§3.9](#39-channel-names). **[obs]**

The README's guess that these correspond to *different mixer modes* is **wrong**: a single
mute press emits **both forms concurrently** on MIDI 1 (2 presses → 2 Form A + 2 Form B).
Form B is the console mirroring the change into backup memory, not an alternate mode.
**[obs]**

A 5-byte message `43 10 3E 1A 7F` is emitted regularly (~6/s) and ignored by the bridge.
`0x7F` is not a documented ADDRESS value; a keepalive remains the best guess. **[obs]**

## 3. Message catalogue

Below, `<ch>` is the 0-based channel (see [§6](#6-channel-and-selector-indexing)), `…` are
bytes whose value the current masks do not constrain. Masks are shown as in `main.py`
(decimal, with string/`None` wildcards).

### 3.1 Channel fader — Form A

```text
F0 43 10 3E 7F 01 1C 00 <ch> 00 00 <u> <v> F7
```

- Mask: `CH_FADER = [67, 16, 62, 127, 1, 28, 0, "channel", 0, 0, "u", "v"]`
- Parameter B5 = `0x1C` (28). B6 = 0. B8, B9 fixed 0.
- Value: 14-bit-style pair in B10 (`u`, coarse) and B11 (`v`, fine) — see [§4.1](#41-140-bit-unipolar-faders).
- Decoded: `FaderMoved(channel=ch, normalized=raw/1023)`.

### 3.2 Master fader — Form A

```text
F0 43 10 3E 7F 01 4F 00 <slot> 00 00 <u> <v> F7
```

- Mask: `MASTER_FADER = [67, 16, 62, 127, 1, 79, 0, "L/R", 0, 0, "u", "v"]`
- Parameter B5 = `0x4F` (79).
- B7 = stereo bus slot, observed 0 or 1 ("L/R"; the initial commit noted "v can be 0 or
  1"). The current handler ignores it — both slots drive `/master/gain`. **[obs]**
- Value encoding identical to the channel fader.

### 3.3 Channel mute — Form A and Form B

```text
Form A: F0 43 10 3E 7F 01 1A 00 <ch> 00 00 00 <val> F7
Form B: F0 43 10 3E 1A 04 5A 00 <ch> 00 00 00 <val> F7
```

- Masks: `MUTE_1 = [67, 16, 62, 127, 1, 26, 0, "channel", 0, 0, 0, "mute"]`,
  `MUTE_2 = [67, 16, 62, 26, 4, 90, 0, "channel", 0, 0, 0, "mute"]`
- Parameter B5: `0x1A` (26) in Form A, `0x5A` (90) in Form B.
- `<val>` (B11) ∈ {0, 1}: **1 = unmuted (sound on), 0 = muted** — re-confirmed on device
  (channel left muted reports 0). Form A and Form B always fire together for the same
  press. **[obs]**

### 3.4 Master mute — Form A and Form B

```text
Form A: F0 43 10 3E 7F 01 4D 00 <slot> 00 00 00 <val> F7
Form B: F0 43 10 3E 1A 04 5E 00 <slot> 00 00 00 <val> F7
```

- Masks: `MASTER_MUTE_1 = [67, 16, 62, 127, 1, 77, 0, None, 0, 0, 0, None]`,
  `MASTER_MUTE_2 = [67, 16, 62, 26, 4, 94, 0, None, 0, 0, 0, None]`
- Parameter B5: `0x4D` (77) in Form A, `0x5E` (94) in Form B.
- `<val>` semantics identical to channel mute.

### 3.5 Pan — Form A

```text
F0 43 10 3E 7F 01 1B 00 <ch> <sign> … … <val> F7
```

- Mask: `PAN = [67, 16, 62, 127, 1, 27, 0, "channel", None, None, None, "pan"]`
- Parameter B5 = `0x1B` (27). B6 = 0.
- Value: bipolar sign+magnitude in B8 (sign) and B11 (value) — see [§4.2](#42-bipolar-pan--surround-xy).
- B9 and B10 are not constrained by the mask; their content is unrecorded (probably 0).
  **[hyp]**

### 3.6 Surround X / Y — Form A

```text
X: F0 43 10 3E 7F 01 25 05 <ch> <sign> … … <val> F7
Y: F0 43 10 3E 7F 01 25 06 <ch> <sign> … … <val> F7
```

- Masks: `X = [67, 16, 62, 127, 1, 37, 5, "channel", None, None, None, "X"]`,
  `Y = [67, 16, 62, 127, 1, 37, 6, "channel", None, None, None, "Y"]`
- Parameter B5 = `0x25` (37), shared by both axes; **B6 selects the axis: 5 = X, 6 = Y**. **[obs]**
- Value: same bipolar encoding as pan. On the console these are the surround-pan X/Y
  parameters of the channel.

### 3.7 EQ band 1 — Form A

```text
Channel: F0 43 10 3E 7F 01 20 <param> <ch> … … <u> <v> F7
Master:  F0 43 10 3E 7F 01 52 <param> <lr> … … <u> <v> F7
```

- Mask: `EQ_BAND_1 = [67, 16, 62, 127, 1, "Sel", "Param", "Ch", None, None, "u", "v"]`
- B5 = selector: **`0x20` (32) = channel EQ (bands of channels 1–16), `0x52` (82) = master
  L/R EQ**. **[obs]**
- B6 = parameter within the band: **3 = gain, 2 = frequency, 1 = type/Q**. **[obs]**
- B7 = channel (0–15) for the channel selector, or L/R (0/1) for the master selector.
- B10/B11 = value; encoding depends on the parameter — see [§4.3](#43-eq-values).
- Bands 2–4 are **not yet captured** — see [§5.2](#52-eq-band-mapping-01v96i--holophonix) for
  the hypothesis.

### 3.9 Channel names

`43 10 3E 1A 02 04 <index> <channel> 00 00 00 <ascii>` — Patch-data space, element `0x04`.
The **Parameter no. is a character index** and the data byte is plain ASCII. **[obs]**

| Index | Field |
| --- | --- |
| 0–3 | Short name, 4 characters, space padded |
| 4–19 | Long name, 16 characters, space padded |

Indices 20–23 do not answer, so 20 slots exist per channel.

**Only B7 0–31 have names** — the 32 mono channels. Probing all 64 channel bytes, nothing
in the ST-IN range (32–39) answers, so the four stereo inputs have no name here and need a
label from elsewhere. Unnamed channels return the console's default, e.g. `CH17`. **[obs]**

Two useful properties, both observed:

- **Only changed characters are transmitted.** Renaming a channel emits one message per
  character that differs, not the whole field.
- **They answer parameter requests.** A request with MODEL `1A` / ADDRESS `02` returns the
  character, so all names can be read on demand rather than waiting for an edit:
  `F0 43 30 3E 1A 02 04 <index> <channel> F7`. Reading all 32 channels costs 640 requests,
  measured at roughly 600 ms — worth fetching once at startup rather than per view.

### 3.10 Remote metering

A separate message class from parameter changes: **element `0x21`** addressed by a
three-byte meter page, requested like a parameter request but with a two-byte count.

```text
F0 43 30 3E 1A 21 <page> 00 00 00 20 F7     -- request: stream page for 10 s
F0 43 10 3E 1A 21 <page> 00 00 <levels…> F7  -- reply, one every ~60 ms
```

One request makes the console stream a bulk frame every ~60 ms for **10 s**; re-request
to keep it running. The page is the first address byte: **[obs]**

| Page | Contents |
| --- | --- |
| `0x00` | The 32 channel **input** levels — pre-fader, pre-mute |
| `0x04` | Stereo master, L and R |
| `0x01`, `0x02`, `0x05` | 8 levels each — unidentified; zero on a desk with no aux/bus signal |

Levels are **14-bit**, two 7-bit bytes each, MSB first, starting at B8. Open inputs read
~90–150 (preamp noise), so the scale is much finer than the front panel's segments.

Facts worth keeping:

- The console does **not** echo the request back (its parameter-change ECHO setting does
  not cover this class).
- The reply carries **SUB STATUS `1n`** (`0x10`), not the request's `3n`.
- kryops/01v96-remote documents this class with model `0x0D` and a different data layout;
  this desk answers model `0x1A` and the layout above. **[obs]**

### 3.8 Ignored message

```text
F0 43 10 3E 1A 7F F7
```

- Exact match on the 5-byte payload `(67, 16, 62, 26, 127)`; dropped silently. Emitted
  regularly by the console. **[obs]**

## 4. Value encodings

### 4.1 The data field

B8–B11 are **one 28-bit two's-complement integer**, seven bits per byte, most significant
first. This single rule replaces every per-message formula the bridge used to carry. **[doc]**

```python
raw = (b8 << 21) | (b9 << 14) | (b10 << 7) | b11
if raw >= 1 << 27:
    raw -= 1 << 28
```

Negative values are why the leading bytes read `0x7F` — they are sign extension, not a
"sign byte". Verified against captures: full-left pan `00 00 7F 7F 7F 41` = −63 exactly.
Implemented as `SysexHandler.decode_value()`. **[obs]**

### 4.2 Faders — position index

`raw` is a **fader position index**, not a dB value. Measured on the console:

| raw | Channel fader | Stereo / bus / aux master / aux send |
| --- | --- | --- |
| 0 | −∞ | −∞ |
| 823 | 0.0 dB | −10.0 dB (interpolated) |
| 1023 | +10.0 dB | 0.0 dB |

Channel faders reach +10 dB. The stereo fader, bus faders, aux masters and aux sends all
span the same travel but top out at unity — confirmed on device. `SysexHandler.fader_db(raw, unity_top=)`
selects between the two laws.

**Aux sends** appear when the console is on an AUX layer: the channel faders become sends,
carried on element `0x23` with the aux number in the Parameter no. as `3 × aux − 1`
(aux 1 → 2, aux 7 → 20, aux 8 → 23, all observed). **Aux masters** use element `0x39` with
B7 as the 0-based aux number. Neither has an OSC mapping yet — both are decoded and logged.
Yamaha's exact raw↔dB table is in the unobtainable MIDI Protocol document, so the shape
between the measured anchors uses the IEC 60268-17 console taper rescaled through raw 823
(`SysexHandler.FADER_LAW`). **Exact at the anchors, approximate between them** — the owner
has confirmed the console's own scale is not linear, and refining this is deferred. **[fit]**

Note the historical quirk this resolves: the old masks required `u <= 7`, which silently
dropped every fader position whose value was negative or above 1023. Those were never
corrupt messages.

### 4.3 Pan and surround X / Y

`raw` is **the console's own displayed number**: −63 (full left) … 0 (centre) … +63 (full
right). Centre emits its own message. Normalized as `raw / 63`. **[obs]**

Surround X (element `0x25`, param 5) and Y (param 6) use the identical encoding and the
identical −63…+63 range, confirmed on device. **The two axes are always reported
separately** — a circular move on the joystick produces interleaved single-axis messages,
never a combined one — so a consumer must keep X and Y per channel and emit a position
whenever either changes. **[obs]**

The previous decoding, `v/63 - 2`, carried a constant `+2/63` offset across the whole
negative side: a hair left of centre reported a hair *right*, and full left read −0.968
instead of −1.0. Fixed.

### 4.4 EQ values

- **Gain** — `raw` is in **tenths of a dB**: 180 = +18.0 dB. Confirmed on device (the old
  `u*127+v / 178` fit read 18.20 dB at the console's −18.0 mark). **[obs]**

- **Frequency** — single byte, logarithmic:

  ```text
  v in [5 .. 124]
  freq_Hz = 21.2 * (20000 / 21.2) ** ((v - 5) / 119)     # 21.2 Hz .. 20 kHz
  ```

  The raw range is confirmed on device: sweeping a band's frequency across its full travel
  spans exactly `5 … 124`, the endpoints the formula assumes. The Hz values at those
  endpoints come from the console display reading correctly rather than from the wire.
  **[obs]** for the range, **[fit]** for the Hz endpoints.

- **Type / Q** — type and Q share **one** parameter. Values `0..40` are bell Q
  (`Q = 10 * 0.01 ** (raw / 40)`, so 0 → Q 10 and 40 → Q 0.1); the non-bell filter types sit
  at the top of the range, where the control stops. It does **not** wrap.

  The type codes are **global**; each band exposes only the two that apply to it. **[obs]**

  | Code | Type | Offered by |
  | --- | --- | --- |
  | 41 | Low shelf | Band 1 |
  | 42 | High shelf | Band 4 |
  | 43 | LPF | Band 4 |
  | 44 | HPF | Band 1 |

  Confirmed from captures: band 1 emits `0..41` and `44` and never 42/43; band 4 emits
  `0..40`, `42` and `43` and never 41/44.

## 5. EQ specifics

### 5.1 What "band 1" is on the console

The 01V96i has a 4-band EQ per channel (plus a master L/R EQ). This repo has only captured
**band 1** messages so far (`Sel = 0x20` for channels / `0x52` for master). The band-1
filter type is selectable on the console between cut (HPF), shelving and bell — which is
why the type/Q parameter carries both.

### 5.2 EQ band mapping (01V96i → Holophonix)

Holophonix exposes **8 filter slots** per track while the 01V96i has **4 EQ bands**, so the
bridge maps by filter type (from the code comments, matching the current implementation
intent):

| 01V96i band | Filter type | Holophonix filter slot |
| --- | --- | --- |
| 1 | HPF / cut | 1 |
| 1 | Shelving | 2 |
| 1 | Bell | 3 |
| 2 | any | 4 |
| 3 | any | 5 |
| 4 | cut | 6 |
| 4 | shelving | 7 |
| 4 | bell | 8 |

**The band 4 rows are disputed.** The table above follows the original code comments. The
project's earlier EQ notes had band 4 the other way round — bell → 6, shelving → 7, LPF → 8
— i.e. ascending by filter type rather than descending. Nothing on the wire settles it;
it depends on how the Holophonix filter slots are actually configured, which is a decision
about the Holophonix side rather than a protocol question.

**Current wiring status:** the parser emits the console's own band number (1–4) and the
Holophonix backend uses it directly in the address, so no type-dependent slot routing
happens at all. Implementing the table above means the backend keeping each band's filter
type and re-addressing gain/frequency/Q when it changes. REAPER's ReaEQ, by contrast,
is addressed by slot name (`hipass`, `loshelf`, `band/@`, `hishelf`, `lopass`), which maps
onto the console's model directly.

### 5.3 Parameter numbers of bands 1–4 — resolved

All four bands live under an EQ element — `0x20` channel, `0x3C` aux, `0x52` master — and
are distinguished by **Parameter no.**, in contiguous blocks. The three elements share the
identical parameter layout, so one table decodes all of them. A bus EQ element very likely
exists on the same pattern but has not been seen. Bands 1 and 4 own an extra parameter because the
console repurposes their gain knob as the filter's on/off switch when they are set to
HPF/LPF respectively.

| Band | Q / type | Frequency | Gain | Filter on/off |
| --- | --- | --- | --- | --- |
| 1 | 1 | 2 | 3 | 4 |
| 2 | 5 | 6 | 7 | — |
| 3 | 8 | 9 | 10 | — |
| 4 | 11 | 12 | 13 | 14 |

**Parameter 15 is the whole-EQ ON/OFF bypass** (values 0/1), sitting immediately after
band 4's enable — which is why the per-band blocks stop at 14. It is distinct from the
bands 1/4 enable, which switches only their HPF/LPF. **[obs]**

The EQ page's **ATT** trim is not part of this element at all: it lives on element `0x1D`
param 0, encoded in tenths of a dB like EQ gain, spanning −96.0 … +12.0 dB. **[obs]**

Twelve of the fourteen are **[obs]**. Only params **9** and **12** (band 3 and band 4
frequency) have not been seen on the wire; they sit between observed neighbours on both
sides, so they are **[fit]** with high confidence.

This supersedes the old guess of sequential *element* numbers `0x21`–`0x23` for bands 2–4,
which was wrong: the band lives in the Parameter no., not the Element no.

## 6. Channel and selector indexing

- B7 in channel messages is **0-based** and follows the Reference Manual's numbering
  (`0:CH1–31:CH32, 32:ST-IN1L–39:ST-IN4R`) exactly:

  | B7 | Meaning | Exposed as |
  | --- | --- | --- |
  | `0…31` | Mono channels CH1–CH32, across the 1–16 and 17–32 layers | tracks 1–32 |
  | `32…39` | ST-IN 1L, 1R, 2L, 2R … 4R | tracks 33–36 (L slot only) |

  Channel 17 was observed at B7 = 16 on the 17–32 layer, so the full 0–31 range is real on
  this console even though only 16 faders are physical. The two sides of each ST-IN pair are
  **linked** — all 77 observed L/R pairs carried identical values — so the bridge acts on the
  L slot and ignores the R. This applies to **every** channel control: fader, mute, pan,
  surround X/Y, EQ and solo all use the same B7. **[obs]**

  **Writing follows the inverse mapping** (`protocol.channel_byte()`): track index 32–35 →
  ST-IN 1L–4L, bytes 32, 34, 36, 38. Writing a *track index* directly as B7 is off by one
  pair from ST-IN 2 up — index 33 is ST-IN 2 to the bridge but B7 33 is ST-IN **1R**. **[obs]**
- `SysexHandler.is_channel_byte()` decides what the masks accept; `channel_index()` maps B7
  to a 0-based track index, returning `None` for the R slot that should be dropped.
- Master messages use B7 as an **L/R slot selector**. The console emits **both slots** for
  every master change — fader, mute (Form A and Form B) and EQ — always carrying identical
  values, since the stereo pair is linked. The bridge acts on slot 0 and ignores slot 1,
  which previously caused every master change to be sent to OSC twice. **[obs]**
- Whether buses/auxes/remote layers beyond channels 1–16 emit their own messages is
  unknown. **[hyp]**

## 8b. Reading the console's state

A **parameter request** is the same message with SUB STATUS `3n` instead of `1n` and no
data bytes (Reference Manual §2.8.3.3). The console replies with the corresponding
parameter change, so replies arrive through the normal decode path and need no special
handling.

Measured on device: **[obs]**

- Requests sent to the **Rx PORT** are answered on the **Tx PORT** — the roles the console's
  own settings name.
- No throttling is needed. 32 requests issued back to back were all answered, the first
  reply after 7 ms and the last after **16 ms**.
- `encoder.state_requests()` covers everything the parser understands — 805 requests, which
  the bridge issues in one burst at startup with `--sync`. That produced 535 OSC messages
  from real console state in under a second.

This is what lets the bridge start in sync rather than blind: without it nothing downstream
knows where a fader is until someone moves it.

## 9. Capturing new parameters

The workflow that actually found the aux, bus and solo support:

```bash
python3 tools/monitor.py        # live TUI; unknown messages are highlighted
```

Move one control at a time on the console. Anything the bridge cannot decode shows as
UNKNOWN with its element number, parameter number, channel and value — which is usually
enough to identify it on the spot. Every run also writes a JSONL log to `captures/`, so the
session can be analysed afterwards:

```python
import json
rows = [json.loads(line) for line in open("captures/monitor_<timestamp>.jsonl")]
```

Useful analyses on that log: group by `(element, parameter)` to see which controls appeared;
look at value ranges to spot the encoding; and measure how long each value was held to find
where the operator deliberately paused, which is how the band 4 filter type codes were read
off without anyone writing anything down.

For bulk capture without a terminal UI, `tools/capture.py` does the same annotation and
logging non-interactively.

Once identified: record the layout in §3 and the encoding in §4 **before** writing the
mask/decoder, then add a regression test using the captured bytes.

## 10. Where this lives in the code

The protocol layer is a standalone package with no MIDI or OSC dependencies:

| Module | Contains |
| --- | --- |
| `yamaha01v96i/protocol.py` | Framing constants, `decode_value`/`encode_value`, channel |
| | numbering, the fader laws, EQ tables. Pure functions over `list[int]`. |
| `yamaha01v96i/events.py` | Frozen dataclasses backends consume; each keeps `raw` so captures can be replayed. |
| `yamaha01v96i/parser.py` | The `MESSAGES` table (template, guard, factory) plus `parse()` |
| | and `identify()`. Adding a control means one row here. |
| `backends/holophonix.py` | The only place Holophonix addresses live. |
| `midi/ports.py` | Port listing, selection, keepalive detection. |
| `midi/midi_sysex.py` | The listening loop. |
| `main.py` | CLI and wiring only. |

Order in `MESSAGES` matters — first match wins, so the keepalive stays first and the
broad EQ match last.

Live inspection: `tools/monitor.py` (curses TUI); bulk capture: `tools/capture.py`. Both
call `yamaha01v96i.parse()`/`identify()`, so they cannot drift from the bridge.

`tests/test_golden_dispatch.py` replays 346 real captured messages through the parser and
backend and asserts the resulting 215 OSC calls against a snapshot — this is what makes
restructuring safe. Regenerate deliberately with `--update` and review the diff.
